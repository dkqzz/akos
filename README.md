# Вариант №30: Роботы на складе

Имитация автоматизированного склада на C17 для Linux. Основная программа
использует потоки POSIX, мьютексы и семафоры. Для сравнения в проекте есть
вторая программа с условными переменными.

## Сборка

```sh
./scripts/build.sh
```

Исполняемые файлы находятся в `build/warehouse_sim` и
`build/warehouse_sim_cond`, тесты — в `build/warehouse_tests`.

## Запуск

Основной вариант:

```sh
./build/warehouse_sim --config data/demo.cfg --log demo.log --delay 0
```

Вариант с условными переменными:

```sh
./build/warehouse_sim_cond --config data/demo.cfg --log demo-cond.log --delay 0
```

Доступны параметры:

```text
--config PATH    конфигурация склада
--log PATH       файл журнала
--seed N         начальное значение генератора
--delay MS       задержка между тактами
--max-ticks N    предел числа тактов
--quiet          не выводить события и карту в терминал
--help           справка
```

Демонстрационные запуски:

```sh
./scripts/run_demo.sh
./scripts/run_demo_cond.sh
```

## Многопоточная модель

Главный поток выполняет роль диспетчера и контроллера тактов. Для каждого робота
создаётся отдельный поток POSIX. В начале такта диспетчер назначает ожидающие
задания и будит рабочие потоки. Роботы одновременно выполняют один переход:
движение, ожидание, загрузку, выгрузку или зарядку. После подтверждений всех
роботов контроллер проверяет инварианты, печатает карту и переходит к следующему
такту.

Общее состояние склада защищено мьютексом. Основная программа использует по два
семафора на робота для пробуждения и подтверждения шага. Программа
`warehouse_sim_cond` использует тот же протокол, но заменяет семафоры на
условные переменные. Вывод в терминал и журнал защищён отдельным мьютексом.

## Многопроцессные варианты

Для оценки 4–5 запускаются дочерние процессы с именованными POSIX-семафорами:

```sh
./build/warehouse_sim_proc_named --config data/demo.cfg --log named.log --quiet
```

Вариант для оценки 6 использует неименованные семафоры в общей памяти:

```sh
./build/warehouse_sim_proc_unnamed --config data/demo.cfg --log unnamed.log --quiet
```

Для оценки 7–8 запустите независимые процессы одной командой:

```sh
./scripts/run_process_shm.sh --config data/demo.cfg --log process.log
```

Скрипт запускает контроллер и отдельный процесс для каждого робота. Контроллер
хранит модель в общем файле `/tmp`, а процессы передают шаги и сигналы через
именованные семафоры. Запуск отдельного контроллера без роботов завершится после
таймаута: он ждёт, пока подключатся все роботы из конфигурации.

## Формат конфигурации

Параметры задаются строками `ключ=значение`. Карта задаётся несколькими строками
`grid=` длиной `width`. Символы карты:

| Символ | Обозначение         |
| ------ | ------------------- |
| `.`    | проход              |
| `#`    | препятствие/стеллаж |
| `P`    | получение           |
| `D`    | выдача              |
| `C`    | зарядка             |
| `N`    | узкий проход        |

```text
width=14
height=8
grid=##############
...
robot=1,row,col,capacity,energy,max_energy
task=101,pickup_row,pickup_col,dropoff_row,dropoff_col,weight
```

Параметры `robot` и `task` можно повторять. CLI имеет приоритет над значениями
конфигурации.

## Завершение и журнал

Работа завершается после разрешения всех заданий, достижения `--max-ticks` или
получения `Ctrl+C`. При прерывании контроллер будит ожидающие потоки, дожидается
их завершения и записывает итоговую строку в журнал.

```text
SUMMARY reason=all tasks resolved ticks=13 assigned=3 completed=3 unreachable=0 moves=26 waits=0
```

Конфигурация `impossible.cfg` демонстрирует корректное завершение с невыполнимым
заданием, а `energy.cfg` - зарядку робота перед движением.

## Тесты

```sh
./scripts/run_tests.sh
```

Проверяются BFS вокруг препятствий, доставка, грузоподъёмность, энергия,
коллизии, загрузка конфигурации, зарядка, потоковый конфликт роботов,
целостность журнала, оба backend-а синхронизации и завершение по сигналу.
Дополнительно `ctest` проверяет доставку в трёх процессных вариантах и остановку
по сигналу.

## ИДЗ №4 — склад по TCP

Сборка та же (`./scripts/build.sh`). Сервер, роботы и наблюдатели запускаются
независимо. Пример на одной Linux-машине:

```sh
./build/warehouse_tcp_server --ip 127.0.0.1 --port 9000 --config data/demo.cfg --log tcp.log --delay 500 --connect-timeout 60000
```

Пока сервер ждёт роботов, в другом терминале запустите:

```sh
./build/warehouse_tcp_observer --ip 127.0.0.1 --port 9000
```

Запустите по клиенту на каждый ID из конфигурации:

```sh
./build/warehouse_tcp_robot --ip 127.0.0.1 --port 9000 --id 1 &
./build/warehouse_tcp_robot --ip 127.0.0.1 --port 9000 --id 2 &
./build/warehouse_tcp_robot --ip 127.0.0.1 --port 9000 --id 3 &
wait
```

Для показа переподключения запустите двух наблюдателей. Остановите одного через
`Ctrl+C` и выполните его команду снова. Для показа переподключения робота
запустите его в отдельном терминале, остановите после появления `carrying=1` и
сразу запустите с тем же `--id`. Чтобы было время на демонстрацию, увеличьте
`--delay` до 1500 мс. Для показа завершения всех клиентов нажмите `Ctrl+C` в
терминале сервера во время работы.

Для распределённого запуска укажите серверу `--ip 0.0.0.0 --port 9000` или адрес
его сетевого интерфейса. На других машинах передайте клиентам IPv4-адрес этого
сервера и тот же TCP-порт. Конфиг склада и журнал нужны только серверу.

| Параметр сервера              | Поведение                                                                                                                                                                                       |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--ip IPV4`, `--port PORT`    | По умолчанию `127.0.0.1:9000`. Порт `0` выбирает свободный порт, который сервер печатает в строке `LISTEN`.                                                                                     |
| `--config PATH`, `--log PATH` | По умолчанию `data/demo.cfg` и `tcp.log`.                                                                                                                                                       |
| `--delay MS`, `--max-ticks N` | По умолчанию задержка 100 мс, предел тактов берётся из конфига.                                                                                                                                 |
| `--connect-timeout MS`        | По умолчанию 10000 мс. Сервер ждёт всех роботов перед первым тактом. После срока может начать с подключёнными. Если после старта отключились все роботы, время ожидания возобновления такое же. |
| `--response-timeout MS`       | По умолчанию 2000 мс. Клиент-робот, пропустивший срок ответа на такт, отключается и может подключиться снова.                                                                                   |
| `--no-observers`              | Режим на 4–5. Клиенты выводят свои состояния, сервер выводит события диспетчера и итог.                                                                                                         |

Сервер заканчивает работу при выполнении или признании заданий невыполнимыми, по
лимиту тактов, `SIGINT` или `SIGTERM`. Если по истечении времени ожидания работа
остаётся и роботов в сети нет, сервер завершает запуск с ошибкой. При завершении
сервер отправляет подключённым клиентам `STOP`. Клиент также можно остановить
отдельно через `Ctrl+C`.

Тесты по реальному TCP требуют Python 3 и разрешения слушать локальный порт:

```sh
./scripts/build.sh
python3 scripts/test_tcp.py build
```

При наличии Python 3 этот сценарий также входит в `ctest`.
